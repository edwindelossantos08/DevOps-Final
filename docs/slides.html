El problema que resuelve un pipeline

Sin pipeline

  • El despliegue es manual y distinto cada vez.
  • Los errores se descubren en producción.
  • Nadie sabe si el servicio está sano hasta que un usuario reclama.
  • Volver atrás es improvisar bajo presión.

Con pipeline

  • Cada commit atraviesa las mismas seis puertas, siempre.
  • El fallo aparece en menos de un minuto.
  • Métricas, logs y alertas responden por el servicio.
  • El rollback es un comando con el SHA del commit.

Arquitectura de la aplicación

Navegador (HTML/CSS/JS, sin frameworks)
        │  HTTP / JSON
        ▼
Express ── middlewares ── rutas ── controladores ── servicio ── SQLite
             │                                        (toda la lógica de negocio)
             ├─► métricas Prometheus  /metrics
             └─► logs JSON con requestId  (Winston)
  • Arquitectura en capas: los controladores no ejecutan SQL; el servicio no conoce Express.
  • Esa separación permite 31 pruebas unitarias sin levantar un servidor.
  • app.js construye la aplicación, server.js la arranca: Supertest monta app directamente.

Tres decisiones que defendemos

1 · Validación en paralelo

Feedback de fallo en ~1 min en lugar de ~3. En un pipeline se optimiza el tiempo hasta el fallo, no hasta el éxito.

2 · Los PR no publican

Código propuesto no es código aceptado. No debe poder inyectar artefactos en el registro antes de la revisión.

3 · Smoke tests reales

Jest valida el código; no detecta que el Dockerfile olvidó copiar public/. Son verificaciones distintas.

Detalle que demuestra criterio: cardinalidad

Las rutas se normalizan a /api/tasks/:id en lugar de /api/tasks/42. Sin eso, mil tareas generarían mil series temporales y Prometheus se degradaría. En Promtail solo level, route y statusCode se promueven a etiquetas de Loki.

Lecciones aprendidas

  • Automatizar temprano cuesta menos que automatizar tarde. Montamos el pipeline con la aplicación a medias; cada funcionalidad posterior nació ya validada.
  • La observabilidad se diseña, no se añade. El requestId, la normalización de rutas y la separación liveness/readiness son decisiones de la aplicación, no del stack de monitoreo.
  • Los smoke tests cubren un hueco que las unitarias no ven. Nuestro primer contenedor pasaba npm test y devolvía 404 en /: el .dockerignore excluía public/.
  • Una alerta ruidosa es peor que ninguna alerta. La primera versión disparaba LatenciaAlta en cada despliegue.
  • La documentación operativa se escribe pensando en el incidente, no en la arquitectura.
